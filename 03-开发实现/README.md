# 03 开发实现

> 阶段问题：**"怎么把设计变成高质量、可维护、可协作的代码？"**
> 编码只占软件项目的一小部分时间；**沟通、评审、重构、自动化**才是开发阶段的主旋律。

---

## 1. 目标

- 按设计文档实现全部功能，**代码通过评审与单测**后合入主干。
- 保持代码**可读、可测、可维护**，让新人能接手，让三个月后的自己能看懂。
- 把"个人自测 → 代码评审 → 集成测试"做成日常习惯，而不是发布前突击。

## 2. 输入 / 前置条件

- 已评审通过的设计文档（接口、数据模型、伪代码）。
- 开发环境就绪：代码仓库、本地环境、CI 流水线（可先建最小版本）。

## 3. 行动步骤

### 3.1 搭建工程骨架

1. 初始化 Git 仓库，配置 `.gitignore`、LICENSE、README。
2. 建立标准目录结构（按团队规范或框架约定）。
3. 配置**依赖管理**（npm / pip / Maven 等）与锁文件，保证环境可复现。
4. 配置 **CI 最小流水线**（提交即构建 + 跑单测），哪怕只有 20 行配置，也要第一天就有。
5. 写好本地开发文档：如何跑起来、如何跑测试、如何调试。

### 3.2 分支策略

推荐 **主干开发 + 功能分支 + PR 合入**（小型团队）：

```
main（主干，永远可部署）
 └── feat/user-login（功能分支：每个任务一条）
       └── PR 评审通过 → 合入 main
```

- 分支命名：`feat/xxx`、`fix/xxx`、`refactor/xxx`、`docs/xxx`。
- 功能分支从主干拉出，**小而短**（1~3 天），避免长期分支导致的合并地狱。
- 需求复杂的团队可加 `dev` 集成分支，但**主干必须永远可部署**。

### 3.3 编码规范

- 统一风格：语言官方风格 / ESLint 等工具强制（工具自动检查，不靠人肉争论）。
- 命名即文档：函数名表达意图（`getUserByEmail` 好过 `getData`）。
- 注释写**为什么**，不写**是什么**（代码本身就说明了是什么）。
- 公共代码（工具函数、常量、错误码）放共享位置，**消灭复制粘贴**。
- 提交信息遵循 Conventional Commits：

```
feat: 新增扫码支付功能
fix: 修复订单金额精度丢失问题
docs: 更新部署文档
refactor: 重构用户认证逻辑
```

### 3.4 开发内循环（每天重复）

```
1. 从看板取任务 → 在功能分支上开发
2. 先写或同步写单元测试（关键逻辑必须覆盖）
3. 本地跑测试全绿 → 提交（小步提交，一次提交一件事）
4. 推送 → 发起 PR → 自己先自审一遍（换位思考：这代码别人看得懂吗？）
5. 评审通过 → 合入 → CI 全绿 → 更新看板任务状态
```

- **TDD（可选但强烈推荐）**：先写失败的测试，再写让它通过的代码。测试即设计的反馈器，也能强制写出可测试的代码结构。
- **童子军规则**：每次改动顺手改善周围的小瑕疵（重命名、删死代码），代码不会越用越烂。

### 3.5 代码评审（PR Review）

- 评审对象：功能、逻辑正确性、边界处理、性能隐患、安全性、可读性、测试覆盖。
- 评审态度：**针对代码，不对人**。提出问题时给建议或问"这里为什么这么做？"。
- 评审时限：**当天评审完**，别让分支"凉"了——凉了的分支必然合并冲突。
- 小型团队至少：每个 PR 有 1 名评审人；核心模块 2 名。

PR 模板示例：

```markdown
## 关联需求
FR-03 扫码支付

## 改动内容
- 新增支付网关客户端
- 订单表增加支付字段

## 测试情况
- 单测：新增 12 个，全部通过
- 手工验证：微信支付回调流程已本地模拟验证

## 需要注意
- 支付回调要求接口幂等，已处理重复回调
```

### 3.6 集成与自测

- 每天至少合入一次主干（保持主干健康，而不是攒一周再合并）。
- 联调：前后端按接口文档联调，发现接口问题先改**接口文档**再改代码。
- 环境自测：测试环境部署后，开发自跑一遍主流程（冒烟测试）。

## 4. 本阶段出口标准（DoD）

一个任务完成 = 以下全部为真：

- [ ] 功能已实现，符合接口设计
- [ ] 单元测试已写并通过（关键路径覆盖率 ≥ 80%）
- [ ] 代码评审通过，评审意见已处理
- [ ] CI 构建与测试全绿
- [ ] 无遗留 P0/P1 缺陷
- [ ] 接口文档/使用文档已同步更新
- [ ] 已合入主干，看板状态已更新

## 5. 常见误区

- ❌ "先跑通再说，注释后面补"——不存在的，后面永远不会补。
- ❌ 攒大量改动再一次性提交——评审难、出问题难定位。小步提交。
- ❌ 只写代码不写测试——测试不是额外负担，它是你明天的"文档"和"安全网"。
- ❌ 评审走过场（"LGTM"）——评审的价值在提问，不是盖章。
- ❌ 修 bug 只改一行、不写回归测试——同样的 bug 下个迭代会再回来。
