# 00 项目管理

> 全程贯穿所有阶段的一层。它的作用不是"管人"，而是**让团队始终清楚：目标是什么、谁负责、什么时候完成、有什么风险**。

---

## 1. 目标

- 把模糊的想法变成**清晰的任务清单**（WBS）。
- 为每个任务定**负责人、截止时间**。
- 提前发现**风险**并准备对策，而不是出事后再救火。
- 保持**节奏**：迭代、会议、发布按计划走。

## 2. 前置条件

- 有一个明确的项目愿景（哪怕一句话）："我们要为谁解决什么问题"。
- 管理层或需求方愿意投入时间参与规划。

## 3. 行动步骤

### 3.1 定义项目范围与成功标准（项目启动时）

1. 写一段《项目章程》：目标、范围（做什么/不做什么）、里程碑、成功标准。
2. 确定干系人（利益相关方）：谁出资、谁提需求、谁使用、谁验收。
3. 明确成功标准示例：
   - 业务：上线 3 个月内注册用户达 X；
   - 质量：缺陷密度 < Y；
   - 时间：Z 日期前交付核心功能。

### 3.2 工作分解（WBS）

把大目标拆成可交付、可估算的任务：

```
项目
├── 需求阶段
│   ├── 访谈用户
│   ├── 编写需求文档
│   └── 需求评审
├── 设计阶段
│   ├── 架构设计
│   └── 数据库设计
├── 开发阶段
│   ├── 用户模块（负责人 A）
│   ├── 订单模块（负责人 B）
│   └── 支付模块（负责人 C）
└── 测试与发布
```

拆解原则：
- 每个任务能由**一个人**在 1~5 天内完成；
- 每个任务有**明确的可验收产物**；
- 拆分到"下一层级可以开始估时"为止。

### 3.3 估算与排期

- **估算方法**：
  - 类比法：参考过去做过的类似任务耗时；
  - 三点估算：`(乐观 + 4×最可能 + 悲观) / 6`；
  - 相对估算：用故事点（小/中/大）替代绝对小时数，团队自比。
- **排期**：用看板（列=状态）+ 日历（行=迭代）双视图。
- 排期时务必给**缓冲**：单任务缓冲 20%，迭代之间留出空余。

### 3.4 建立风险登记册

| 编号 | 风险描述 | 概率(高/中/低) | 影响(高/中/低) | 应对措施 | 负责人 | 状态 |
|---|---|---|---|---|---|---|
| R1 | 需求方中途改需求 | 高 | 高 | 设变更流程，重大变更重排期 | 产品 | 跟踪中 |
| R2 | 第三方支付接口延期 | 中 | 高 | 提前对接、准备降级方案 | A | 跟踪中 |

每周例会过一遍登记册，概率/影响变化就更新。

### 3.5 运行节奏（小型团队）

- **每日站会（15 分钟）**：每人三句话——昨天完成 / 今天计划 / 有无阻塞。不解决问题，只暴露问题，会后另约人解决。
- **迭代规划会**：从需求池中挑选下个迭代的任务，逐项确认"完成定义"。
- **迭代评审会**：演示成果给需求方，收集反馈。
- **迭代复盘会**：回顾改进（具体模板见 `07-评审复盘`）。

### 3.6 变更管理

任何改变范围、时间、成本的要求都走同一流程：

```
提出变更 → 记录到变更日志 → 评估影响（范围/排期/风险）
→ 干系人决策（接受/拒绝/推迟）→ 更新计划与看板 → 告知全团队
```

**关键原则：口头变更不算数，必须落到文档。**

## 4. 产出物清单

| 产物 | 时机 | 形式 |
|---|---|---|
| 项目章程 | 启动时 | 1 页文档 |
| WBS 任务清单 | 规划时 | 看板 |
| 迭代计划 | 每次迭代规划会 | 看板 + 日历 |
| 风险登记册 | 全程维护 | 表格（见 3.4） |
| 变更日志 | 有变更时 | 追加表格行 |
| 进度报告 | 每周 | 简短邮件/文档：完成度、风险、下周计划 |

- [ ] 干系人清单已确认

## 6. 常见误区

- ❌ 把项目管理当成"写一堆没人看的计划书"——计划是沟通工具，不是档案。
- ❌ 只看进度不看风险——风险不登记，等于赌运气。
- ❌ 排期没有缓冲——任何项目都会遇到意外，没缓冲的排期必延期。
- ❌ 变更不走流程——这是范围失控和延期的最常见原因。
