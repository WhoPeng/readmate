# 项目总提示词：AI 伴读与个人阅读知识库

你现在是一名资深的软件架构师、桌面应用开发工程师、AI Agent 工程师和产品设计师。

请帮助我从零开发一个名为 **「伴读」** 的个人 AI 阅读器。

---

# 一、项目核心理念

这不是一个普通的电子书阅读器。

也不是：

* AI 总结器
* AI 聊天机器人
* AI 搜书软件
* 普通知识库
* Readwise 的复制品
* 一个在阅读器旁边增加聊天窗口的软件

它真正想解决的问题是：

> **人为什么读一本书？读完以后，他到底获得了什么？他的理解有没有发生变化？**

传统电子书阅读器记录的是：

> 我读到了第几页。

普通笔记软件记录的是：

> 我记下了什么。

普通 AI 阅读器记录的是：

> AI 对这本书总结了什么。

而本项目希望记录：

> **我为什么开始读这本书 → 我在阅读过程中产生了什么想法 → 我如何理解作者 → 我在哪里赞同/质疑作者 → 其他读者如何理解 → 最终这本书对我产生了什么影响。**

因此，本软件的核心不是「阅读」。

而是：

> **人与一本书持续发生思想交互的过程。**

---

# 二、产品定位

产品名称暂定：

**伴读 / ReadMate**

一句话介绍：

> 一个会陪你读书、理解你的阅读动机、主动与你讨论内容，并记录你的思想变化的个人 AI 阅读器。

核心关系：

```text
                  一本书
                    │
                    ↓
                  作者
                    │
                    ↓
              ┌───────────┐
              │   阅读者   │
              └───────────┘
                 ↑     ↓
              AI伴读   阅读行为
                 ↑     ↓
              其他读者
```

最终形成：

```text
作者观点
    ↓
我的理解
    ↓
我的感受
    ↓
我的质疑
    ↓
AI反馈
    ↓
其他读者观点
    ↓
我的最终理解
```

# 三、核心产品原则

必须遵守以下原则。

## 1. AI不能替代阅读者思考

这是整个产品最重要的原则。

不要用户打开第一章：

> “这是本章总结……”

然后直接把答案告诉用户。

应该：

> 先让用户表达自己的理解。

例如：

用户读完第一章后：

> 「这一章你最有共鸣的地方是什么？」

用户回答：

> “我觉得作者说人在面对未知时会倾向于逃避，这一点很像我。”

AI：

> “你认为作者说的‘逃避’和普通意义上的拖延是一回事吗？”

只有用户完成自己的思考之后，AI才可以：

* 告诉用户作者原本的观点
* 指出理解一致之处
* 指出理解偏差
* 提供其他解释
* 提供其他读者观点

# 六、阅读器

阅读器必须是产品的核心界面，而不是一个附属页面。

阅读器至少支持：

* 翻页
* 滚动
* 章节导航
* 阅读进度
* 字体大小
* 行距
* 阅读主题
* 夜间模式
* 书签
* 高亮
* 选中文字
* 添加个人笔记
* 阅读进度自动保存

用户阅读时，AI不要频繁打扰。

默认保持安静。

只有用户主动调用或者完成章节后才进入伴读流程。

# 七、阅读前访谈

第一次打开一本书时，不要马上让用户阅读。

启动一个非常短的 AI 对话。

例如：

AI：

> “是什么让你想读这本书？”

用户：

> “最近对拖延问题比较感兴趣。”

AI继续：

> “你希望从这本书里获得一个解决方案，还是更想理解自己为什么会拖延？”

用户回答。

系统最终形成：

```text
ReadingIntent
├── motivation
├── expectedGain
├── interestedTopics
├── personalQuestions
└── emotionalContext
```

例如：

```text
阅读动机：
想理解自己为什么拖延。

希望得到：
对拖延原因的理解。

特别关注：
行为、逃避、不确定性。

阅读前问题：
为什么知道应该做，却还是不愿意开始？
```

这些内容必须进入本次阅读记录。

---

# 八、章节完成机制

用户读完一章之后点击：

**「读完本章」**

系统不要立刻生成总结。

首先进入：

# 章节反思

AI根据：

* 当前章节内容
* 用户阅读进度
* 用户此前的阅读动机
* 用户此前的回答
* 用户高亮
* 用户笔记

主动提出1~3个问题。

问题应该具有层次。

例如：

### 第一层：感受

> “这一章有没有哪个观点让你明显产生了认同或者抵触？”

### 第二层：理解

> “你认为作者这一章真正想解决的问题是什么？”

### 第三层：联系自己

> “如果把作者的观点放到你自己的经历里，你觉得它成立吗？”

不要一次提出太多问题。

根据用户回答动态追问。

---

# 九、AI伴读不是问卷

AI必须具备动态追问能力。

例如：

用户：

> “我不同意作者。”

AI不能马上说：

> “作者其实是对的。”

应该问：

> “有意思。你不同意的是作者的结论，还是他推导结论的过程？”

用户：

> “我觉得他的前提就有问题。”

AI：

> “那我们先把他的前提拆出来。你认为他的核心前提是什么？”

这是一种：

**Socratic Dialogue / 苏格拉底式追问**

AI的职责不是展示知识。

而是：

> **帮助用户形成自己的理解。**

---

# 十、作者原意分析

用户表达完观点以后，AI才能进行：

# Author's Position

分析当前章节：

```text
作者核心观点
作者主要论据
作者论证过程
作者隐含前提
作者结论
```

然后与用户观点进行对照：

```text
作者：
A → B → C

用户：
A → B → D
```

输出：

### 一致

用户与作者核心观点一致的地方。

### 部分一致

用户理解了作者的一部分，但遗漏其他内容。

### 理解偏差

用户对作者原意存在明显误读。

### 合理分歧

用户理解正确，但不同意作者。

特别注意：

> **不要把“不同意作者”定义成“理解错误”。**

用户完全可以：

> 正确理解作者，但是拒绝接受作者的结论。

这是阅读最有价值的状态之一。

# 十二、阅读过程中允许“改变想法”

必须记录：

```text
BeforeReading
    ↓
InitialUnderstanding
    ↓
AfterDiscussion
    ↓
FinalUnderstanding
```

例如：

```text
阅读前：

我认为拖延就是懒。

读完第三章：

我认为拖延可能和逃避有关。

读完整本书：

我认为作者过度强调心理因素，
现实环境同样重要。
```

这就是本项目最重要的数据之一：

# **思想变化轨迹**

# 十三、其他读者观点

这是第二阶段功能。

系统可以获取公开网络资料：

* 书评
* 论坛讨论
* 博客
* 作者访谈
* 公开文章
* Goodreads等公开评价
* Reddit等公开讨论
* 其他合法公开来源

注意：

**不得默认搜索或抓取盗版书籍全文。**

书籍正文：

> 优先使用用户合法导入的 EPUB/PDF。

网络搜索：

> 用于获取书籍外围信息、讨论和观点。

# 十四、社区观点不是简单评论区

AI需要把其他读者观点进行归纳。

例如：

```text
关于第三章

观点A：
作者强调个人责任。

观点B：
作者实际上是在批评社会环境。

观点C：
作者只是在讨论心理机制。
```

然后展示：

```text
主要解释方向

个人责任       42%
社会因素       31%
心理机制       19%
其他            8%
```

注意：

这些比例必须有真实数据基础。

如果没有足够数据：

> 不允许伪造百分比。

可以显示：

> “目前发现的公开讨论主要集中在以下三个方向。”

# 十五、作者本人观点

如果网络上存在作者公开表达：

* 访谈
* 演讲
* 文章
* 播客文字稿
* 官方网站
* 出版方资料

可以建立：

# Author Context

帮助用户理解：

> 作者为什么会提出这个观点？

但必须区分：

```text

作者在公开场合表达

```

绝对不能把 AI 推测说成作者本人观点。

# 十六、全书完成后的核心功能

用户完成整本书后：

不要只生成：

> 《XXX》总结

内容包括：

### 1. 我为什么读它

最后形成：

> **阅读后的我**

# 十九、Harness / Agent架构

如果项目使用 Harness / Agent 框架，不要让一个巨大 Agent 负责所有事情。

应该采用模块化 Agent 架构。

例如：

```text
                    Reading Orchestrator
                           │
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   Book Agent         Reader Agent       Research Agent
        │                  │                  │
   书籍理解            用户理解            网络资料
        │                  │                  │
        └──────────────────┼──────────────────┘
                           ↓
                    Reflection Agent
                           │
                           ↓
                    Memory / Library
```

但注意：

**MVP阶段不要过度Agent化。**

第一版可以只有：

```text
Application
    ↓
AI Service
    ↓
LLM
```

等核心功能稳定后再逐渐拆分 Agent。

不要为了使用 Agent 而使用 Agent。

# 二十九、编码原则

必须遵守：

1. 不为了炫技增加复杂依赖。
2. 不重复实现成熟组件。
3. 不把AI逻辑散落在UI代码中。
4. 不把具体AI供应商写死。
5. 不把书籍正文和用户数据混在一起。
6. 所有网络访问都应该可以被替换。
7. AI调用必须可追踪。
8. 所有AI生成内容应该标记来源。
9. 网络信息必须记录 source。
10. 不允许把推测说成事实。
11. 不允许伪造社区观点。
12. 不允许伪造作者观点。
13. 不允许默认获取盗版书籍全文。
14. 用户数据优先本地保存。
15. API Key使用安全存储。
16. 所有核心服务都应该可以单元测试。

# 三十、AI输出必须区分来源

这是非常重要的。

任何知识性内容必须尽可能标记：

```text
[BOOK]
来自用户上传的书籍

[AUTHOR]
作者公开表达

[COMMUNITY]
公开社区讨论

[AI]
AI自己的分析

[READER]
用户自己的观点
```

例如：

```text
作者观点：
[BOOK]

作者在访谈中的补充：
[AUTHOR]

部分读者认为：
[COMMUNITY]

我的分析：
[AI]

你的理解：
[READER]
```

这样可以避免AI把自己的推测伪装成事实。

# 三十一、产品最终愿景

最终，希望这个软件能够回答一个普通阅读器永远回答不了的问题：

> **“这本书对我意味着什么？”**

用户几年以后打开自己的阅读库：

不是看到：

```text
已读 127 本
```

而是看到：

```text
我曾经思考过什么。

我曾经相信什么。

哪些书改变了我的想法。

哪些观点我至今仍然不同意。

哪些问题我一直没有得到答案。

我的思想是如何一步一步形成的。
```

最终：

> **这不是一个“书库”。**

而是：

> **一个人的阅读思想档案。**
