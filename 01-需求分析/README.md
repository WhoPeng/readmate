# 01 需求分析

> 阶段问题：**"我们要做什么？为谁做？为什么做？做到什么程度算完成？"**
> 本阶段的一切投入，都是为了减少"做完才发现做错了"的返工——返工是软件项目最大的成本。

---

## 1. 目标

- 把用户的模糊想法转化为**清晰、完整、可测试**的需求描述。
- 与需求方达成一致并**签字确认**（防止日后扯皮）。
- 输出**需求规格说明书（SRS）**，作为设计和验收的共同依据。

## 2. 输入 / 前置条件

- 项目愿景与范围（来自 `00-项目管理`）。
- 干系人名单（谁能提供需求、谁有权拍板）。

## 3. 行动步骤

### 3.1 收集需求（信息来源）

| 方法 | 适用场景 | 要点 |
|---|---|---|
| 用户访谈 | 用户少、需要深挖 | 问"场景"不问"功能"：你目前怎么做的？痛在哪？ |
| 问卷调查 | 用户多、要量化 | 先小范围试发，避免选项歧义 |
| 竞品分析 | 有同类产品 | 列竞品功能表，标注"我们要不要跟" |
| 现场观察/跟单 | 业务流程复杂 | 看真实操作，别只听描述 |
| 原型演示 | 用户说不清时 | 画草图/交互原型，让用户"看到"再确认 |

### 3.2 分析需求

1. **分类**：功能需求（系统做什么）、非功能需求（性能、安全、可用性、兼容性）、约束（技术栈、法规）。
2. **明确角色**：列出所有使用者和外部系统（用户、管理员、第三方 API……）。
3. **写用户故事**（推荐格式）：

```
作为【角色】，我想要【功能】，以便【价值】
示例：作为普通用户，我想要扫码支付，以便不用带现金。

验收标准（可测试的，每一条都是将来测试用例的来源）：
1. 用户扫描商家二维码后，1 秒内跳转到支付页；
2. 余额不足时提示"余额不足"并给出充值入口；
3. 支付成功 5 秒内，订单状态变为"已支付"。
```

4. **画流程图/状态图**：订单状态流转、审批流程等"过程型"需求，一张图胜过一千字。

### 3.3 确定优先级（MoSCoW 法）

| 级别 | 含义 | 处理 |
|---|---|---|
| Must（必须有） | 没有它产品没法用 | 本迭代必须完成 |
| Should（应该有） | 重要但可暂缓 | 有资源就做 |
| Could（可以有） | 锦上添花 | 有空闲再做 |
| Won't（不要做） | 明确排除 | 写进文档防止以后反复 |

### 3.4 编写需求规格说明书（SRS）

标准结构（按需裁剪，小项目可以精简到 3 页）：

```
1. 引言
   1.1 背景与目标
   1.2 术语定义
   1.3 读者与参考文档
2. 总体描述
   2.1 产品定位与用户画像
   2.2 角色清单
   2.3 运行环境（平台、设备、浏览器）
3. 功能需求（按模块组织）
   3.1 模块 A：功能清单 + 用户故事 + 验收标准
   3.2 模块 B：…
4. 非功能需求
   4.1 性能（响应时间、并发量、吞吐量）
   4.2 安全（权限、加密、合规）
   4.3 可用性（容灾、备份、恢复时间目标 RTO）
   4.4 兼容性（浏览器/机型/版本）
5. 约束与假设
   5.1 技术栈约束、团队规模约束
   5.2 明确不做的内容（Out of Scope）
6. 验收方案
   6.1 验收标准（每项需求是否达成如何判定）
   6.2 上线标准
```

### 3.5 需求评审（必须做）

- 参与者：需求方/产品、开发代表、测试代表、设计。
- 评审关注点：**完整性**（有没有漏）、**一致性**（有没有自相矛盾）、**可行性**（技术上做得出来吗）、**可测试性**（每条需求能写用例吗）、**无歧义**（每个人理解是否一致）。
- 评审通过后，需求方**签字/邮件确认**，文档进入基线（之后改动走变更流程）。

### 3.6 建立需求追踪矩阵（RTM，可选但推荐）

需求条目 ↔ 设计条目 ↔ 测试用例 ↔ 代码模块 的映射表，用来回答"这条需求实现了吗？被哪些用例覆盖？"

| 需求编号 | 需求描述 | 设计文档位置 | 测试用例编号 | 实现状态 |
|---|---|---|---|---|
| FR-01 | 扫码支付 | 02-设计/支付模块.md | TC-0101~0105 | 已实现 |

## 4. 需求质量检查：INVEST 原则

每个用户故事应当是：

- **I**ndependent 独立的：尽量不依赖其他故事
- **N**egotiable 可协商的：细节可以讨论
- **V**aluable 有价值的：对用户有明确价值
- **E**stimable 可估算的：团队能估出工作量
- **S**mall 小的：1~5 天内能完成
- **T**estable 可测试的：有明确验收标准

## 5. 本阶段出口标准（DoR，进入设计的门票）

- [ ] SRS 文档完成，评审通过，需求方已确认
- [ ] 每条功能需求都带可测试的验收标准
- [ ] 非功能需求（性能/安全/兼容性）已明确
- [ ] 优先级（MoSCoW）已标出，本迭代范围已锁定
- [ ] 明确记录"不做什么"
- [ ] 需求追踪矩阵已建立（至少建立骨架）
- [ ] 变更流程已告知需求方

## 6. 常见误区

- ❌ 问"你要什么功能"而不是"你要解决什么问题"——用户会给出解决方案而非需求。
- ❌ 需求只口头确认——评审 + 签字，缺一不可。
- ❌ 验收标准写"体验流畅"这种不可测的话——要写"3 秒内完成支付"。
- ❌ 需求阶段拖太久——小步快跑，先锁定核心（Must），边做边细化细节。
