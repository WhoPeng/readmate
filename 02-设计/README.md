# 02 设计

> 阶段问题：**"怎么把需求变成可实现的方案？"**
> 设计分两层：**概要设计（架构）** 定骨架，**详细设计** 定血肉。设计阶段的 1 小时讨论，能省下开发阶段的 10 小时返工。

---

## 1. 目标

- 确定**技术选型**与**系统架构**（概要设计）。
- 把每个模块的内部逻辑、接口、数据结构**定义清楚**（详细设计）。
- 记录关键决策及理由（ADR），让后来者知道"为什么这么设计"。
- 输出能让开发**直接开工、不猜、不打架**的文档。

## 2. 输入 / 前置条件

- 已评审通过的需求规格说明书（SRS）。
- 技术栈约束（团队熟悉的语言、公司已有的基础设施）。

## 3. 概要设计（架构设计）

### 3.1 行动步骤

1. **画系统上下文图**：系统 + 外部实体（用户、第三方 API、数据库、消息队列），看清边界在哪。
2. **模块划分**：按"高内聚、低耦合"拆模块（如：用户、订单、支付、通知）。每个模块写清职责，**不许有"杂项模块"**。
3. **技术选型**：语言/框架/数据库/缓存/部署方式。选型依据写清楚（团队技能、生态、性能、运维成本），别只写结论。
4. **数据设计**：核心实体、关系（ER 图）、存储方案（关系型/文档型/缓存各放什么）。
5. **接口约定**：模块间调用关系、对外 API 风格（REST/gRPC/消息队列）、统一错误码规范。
6. **非功能设计**：性能（缓存、索引、异步化）、安全（认证授权方案、加密）、可用性（冗余、降级、限流）。

### 3.2 分层参考（Web 项目通用）

```
前端层（Web/App）
   │ HTTP/gRPC
接口层（Controller：参数校验、权限）
   │
业务层（Service：业务规则、事务）
   │
数据层（Repository/DAO：持久化）
   │
数据库 / 缓存 / 消息队列
```

原则：**上层只依赖相邻下层**，禁止跨层调用（页面直接拼 SQL 是后期维护噩梦的源头）。

### 3.3 ADR（架构决策记录）

每次重大决策写一个 ADR，每个 10 行左右：

```markdown
# ADR-001：数据库选型 PostgreSQL

- 状态：已接受
- 背景：数据量预估千万级，需要复杂查询和事务
- 决策：采用 PostgreSQL 15
- 理由：团队熟悉；事务与 JSON 支持兼顾；自托管成本可控
- 后果（代价）：运维需要专职 DBA 技能；相比 MySQL 生态资料略少
- 备选方案：MySQL（放弃：JSON 查询弱）、MongoDB（放弃：需要强事务）
```

ADR 的价值：三个月后有人问"为什么不用 XX"，指给他看，省一场争论。

## 4. 详细设计

针对每个模块输出：

| 内容 | 说明 | 推荐形式 |
|---|---|---|
| 模块职责与边界 | 它管什么、不管什么 | 一段文字 |
| 核心类/结构 | 类名、职责、关键字段 | 类图 / 结构体定义 |
| 关键流程 | 一次请求从进来到回去的完整路径 | 时序图 / 伪代码 |
| 接口定义 | 方法、参数、返回值、错误码、示例 | 表格 + 示例请求响应 |
| 数据模型 | 表结构、字段类型、索引、外键 | 建表语句 / ER 片段 |
| 状态机 | 状态流转 + 触发事件 | 状态图 / 表格 |

示例：订单模块关键流程（伪代码）

```
用户提交订单:
  1. 校验库存与价格
  2. 创建订单记录 (状态=待支付)
  3. 生成支付单，调支付网关
  4. 支付回调成功 → 扣库存 → 状态=已支付 → 发消息给物流系统
  5. 支付超时 → 状态=已取消 → 释放库存
```

## 5. 设计评审（必须做）

- 参会：架构师/技术负责人（主持）、开发全员、测试代表。
- 评审清单：
  - [ ] 模块边界清晰，无职责重叠
  - [ ] 依赖方向正确（无环、无跨层）
  - [ ] 接口参数与错误码完备
  - [ ] 数据模型满足功能需求和非功能需求（性能/容量）
  - [ ] 安全：认证、授权、数据校验有方案
  - [ ] 异常与边界情况有设计（超时、重试、幂等、并发）
  - [ ] 扩展性：未来需求（如多语言、多商户）不推翻现有设计
  - [ ] 每个重大决策都有 ADR
- 评审产出：问题清单 → 修改设计 → 复审通过后，设计进入基线。

## 6. 本阶段出口标准

- [ ] 架构文档 + 详细设计文档完成并通过评审
- [ ] 所有模块有明确的接口定义
- [ ] 数据模型已定稿（至少核心表）
- [ ] 关键决策有 ADR 记录
- [ ] 非功能设计（性能/安全/可用性）有方案
- [ ] 风险已登记（如：技术难点需预研的，列入开发阶段首个任务）

## 7. 常见误区

- ❌ 设计文档写完就锁进抽屉——开发期间设计必须"活"：发现更优解时，先改设计文档再改代码。
- ❌ 过度设计——只为当前明确需求设计，YAGNI（你不需要它），别为想象中的未来堆复杂度。
- ❌ 接口只口头约定——前后端各写各的，联调必然爆炸。接口先定义、成文档、再开发。
- ❌ 技术选型不写理由——三个月后没人记得为什么，改也不是、不改也不是。
