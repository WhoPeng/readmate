# 04 测试

> 阶段问题：**"怎么证明软件做对了？怎么在问题到达用户之前抓住它？"**
> 测试不是开发完之后的"质检工序"，而是**从需求阶段就开始的全程活动**。测试的最终目标是建立信心：这个版本可以安全发布。

---

## 1. 目标

- 用**最小的成本**发现**最多的缺陷**，并验证系统满足需求（验收）。
- 提供质量数据，支持"能否发布"的决策（测试报告是发布检查单的入场券）。
- 沉淀自动化用例，让回归测试越来越便宜（否则功能越多，手动回归时间越长，最终回归不起）。

## 2. 输入 / 前置条件

- 需求文档（含验收标准）、设计文档。
- 测试环境（可部署被测版本）。

## 3. 测试金字塔（策略的总纲）

```
         / 端到端 E2E \      ← 少（十几条主流程），贵、慢、脆弱
        / 集成测试     \     ← 中等（模块间交互、数据库、外部接口）
       / 单元测试        \   ← 多（几百上千条），快、便宜、定位准
```

- **单元测试**：测函数/类，毫秒级，覆盖率保底（核心逻辑 ≥ 80%）。
- **集成测试**：测模块协作、数据库操作、第三方接口（mock 化外部依赖）。
- **E2E 测试**：模拟真实用户走完整流程，只覆盖核心业务流（登录、下单、支付、退款）。
- 比例参考：7:2:1。金字塔倒过来（大量 E2E）是团队最常踩的坑——慢且脆，CI 跑不动。

## 4. 行动步骤

### 4.1 测试计划（需求评审后即可写，与开发并行）

内容：测试范围（测什么/不测什么）、测试策略（各层级怎么测）、环境与数据准备、排期、准入/准出标准、风险。

### 4.2 测试设计（核心方法）

| 方法 | 思路 | 示例 |
|---|---|---|
| 等价类划分 | 把输入分成"行为相同"的组，每组测一个 | 年龄输入：有效（18~60）/无效（<18，>60，非数字） |
| 边界值分析 | 测边界及边界两侧 | 金额 0、0.01、最大值、超过最大值 |
| 判定表 | 多条件组合 | 会员等级 × 优惠券 × 支付方式 → 应付金额 |
| 场景法 | 按业务流程走"快乐路径+异常路径" | 下单成功 / 库存不足 / 支付超时 / 支付重复回调 |

每条用例包含：编号、标题、前置条件、步骤、预期结果、优先级。预期结果必须**可判定**（不能写"页面正常显示"）。

### 4.3 测试执行与分层节奏

| 层级 | 时机 | 谁执行 |
|---|---|---|
| 单元测试 | 每次提交（CI 自动） | 开发（自动化） |
| 集成测试 | 每次合入主干后（CI 自动） | 自动化为主 |
| 功能测试 | 每个迭代的功能完成后 | 测试人员（手动 + 自动化） |
| 回归测试 | 每个迭代末、发布前 | 自动化优先，核心流程手动 |
| 性能测试 | 发布前、大版本前 | 测试/运维 |
| 安全测试 | 发布前、涉及资金/隐私的改动 | 专项人员 |
| UAT 验收测试 | 发布前 | 需求方按验收标准逐条确认 |

### 4.4 缺陷管理（Bug 生命周期）

```
发现 → 提交 → 确认(复现) → 修复 → 验证 → 关闭
  ↑          ↓                     ↓
  └────────── 不可复现/重复/无效 ──┘
```

- 缺陷单必备：标题、环境、步骤、实际结果、**预期结果**、严重级别、优先级、截图/日志。
- 级别定义（示例）：
  - P0 阻断：无法登录、数据丢失 → 立即停线修
  - P1 严重：核心功能不可用，有替代方案 → 发布前必须修
  - P2 一般：功能可用但不符预期 → 本迭代修
  - P3 轻微：文案、样式小瑕疵 → 可下迭代修
- **缺陷数据是流程的信号**：某一模块缺陷密度异常高 → 该模块需要重构或加强评审，而不是继续修修补补。

### 4.5 测试报告（阶段出口）

结构：测试范围与执行率、用例结果统计（通过/失败/阻塞）、缺陷统计（按模块/级别分布）、未解决问题清单及风险评估、**发布建议（建议发布 / 有条件发布 / 不建议发布）**。

## 5. 本阶段出口标准

- [ ] 计划内用例 100% 执行（或明确说明未执行原因）
- [ ] P0/P1 缺陷清零；P2 有明确的解决或挂起理由（挂起需负责人批准）
- [ ] 回归测试通过（核心流程无回归）
- [ ] 性能/安全等专项测试完成（如适用）
- [ ] 测试报告已出，发布建议明确
- [ ] 需求追踪矩阵中"测试用例"列已填满

## 6. 常见误区

- ❌ 测试只测"正常路径"——缺陷集中在边界和异常路径。
- ❌ 让开发测试自己的代码——自己写的代码有"盲点"，必须交叉。
- ❌ 只做手动回归——功能一多，手动回归要么漏要么慢，自动化是唯一出路。
- ❌ 发现缺陷直接悄悄修掉不登记——失去质量数据，等于蒙眼开车。
