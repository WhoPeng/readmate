# 05 部署发布

> 阶段问题：**"怎么把验证过的版本安全、可回滚地交付给用户？"**
> 发布的最高原则：**任何一次发布都是小步的、可验证的、可回滚的。** 发布做得越频繁、越自动化，单次发布的风险就越小。

---

## 1. 目标

- 建立 **CI/CD 流水线**，让"提交代码 → 构建 → 测试 → 部署"自动化。
- 建立**多环境链**，测试验证通过后才到生产。
- 每次发布有**检查单 + 回滚预案**，出问题能 5 分钟恢复。

## 2. 输入 / 前置条件

- 代码仓库与 CI 平台（GitHub Actions / GitLab CI / Jenkins 等）。
- 测试通过的报告（来自 `04-测试`）。
- 部署目标环境（服务器 / 容器平台 / 云服务）。

## 3. 环境链（从左到右，环境越右越接近生产）

```
dev（开发环境）→ test（测试环境）→ staging（预发布环境，与生产一致）→ prod（生产环境）
```

原则：

- **环境一致性**：staging 的配置、数据规模、架构与生产尽量一致，否则"测试通过、上线炸锅"。
- **配置与代码分离**：环境相关配置（地址、密钥）不进代码库，用环境变量 / 配置中心管理，密钥进密钥管理服务。
- 每个环境的数据做好隔离：测试环境禁用真实用户数据。

## 4. CI/CD 流水线设计

```
[每次推送] → 构建 → 静态检查/单测 → 生成制品(镜像/包)
[合入主干] → 部署 test 环境 → 自动化集成测试 → 生成发布候选
[打 tag]   → 部署 staging → 验收测试 → 【人工审批】→ 部署 prod
                                          ↓
                                  监控验证 + 回滚预案就绪
```

要点：

- **CI 必须快**（10 分钟内反馈），慢的 CI 会被开发者绕过。
- 流水线失败 = 阻塞合入，不允许"先合后补"。
- 制品（Artifact）**不可变**：test 环境验证过的那个制品，原样部署到 prod，禁止在 prod 重新构建（构建环境不同，结果可能不同）。

## 5. 版本管理

- 语义化版本 SemVer：`主版本.次版本.修订号`（2.3.1）
  - 主版本：不兼容的 API 变更
  - 次版本：向后兼容的新功能
  - 修订号：向后兼容的缺陷修复
- 每次发布写 **CHANGELOG**（What's New），用户和团队都能看。
- Git 打 tag 与版本号对应，保证"哪个版本 = 哪段代码"可追溯。

## 6. 发布策略（按风险选择）

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 直接替换 | 停机替换 | 简单 | 有停机时间 |
| 滚动发布 | 逐个节点替换 | 无停机，逐步生效 | 新旧版本短暂共存，需兼容 |
| 蓝绿发布 | 新环境整套部署，验证后切流量 | 回滚=切回旧环境，最快 | 成本翻倍 |
| 金丝雀发布 | 先给 5% 流量，验证后再全量 | 风险最小，可灰度 | 需要流量控制能力 |

小团队起步建议：**滚动发布 + 数据库兼容策略**；涉及核心交易再上金丝雀。

## 7. 发布检查单（每次发布必走）

- [ ] 发布版本号与 CHANGELOG 已确定
- [ ] 测试报告确认可发布（P0/P1 清零）
- [ ] 数据库变更脚本已评审、有回滚脚本
- [ ] 环境配置与密钥已准备（staging 验证过）
- [ ] 回滚预案已写：回滚命令 + 回滚条件（何时触发）
- [ ] 监控看板与告警已确认（发布后看什么指标）
- [ ] 发布窗口已通知相关方（客服/需求方）
- [ ] 审批人已确认

发布流程：

```
0. 发布前 10 分钟：确认监控正常、当前版本无重大事故
1. 部署（自动化）→ 2. 冒烟验证（自动化脚本 + 关键路径手测）
3. 观察 15~30 分钟关键指标（错误率、延迟、CPU、业务指标）
4. 异常 → 按预案回滚；正常 → 宣布发布成功并记录
```

## 8. 本阶段出口标准

- [ ] 生产版本已部署并冒烟验证通过
- [ ] 发布后观察期无异常（或异常已处理）
- [ ] 回滚预案已保留（发布后 24 小时内不可删除）
- [ ] CHANGELOG 与版本 tag 已更新
- [ ] 发布记录（时间、版本、操作人、结果）已归档

## 9. 常见误区

- ❌ 发布全靠手动点按钮、敲命令——步骤一多必漏必错，全部自动化。
- ❌ 回滚脚本等出事了再写——出事时人最慌，写不出正确脚本。
- ❌ 数据库变更不可回滚（删了列）——大表结构变更先加列、双写、再切换、最后删旧列，分步走。
- ❌ 周五下午发布大版本——出了事故全员加班。重要发布避开周五和长假前。
